## Architecture

`GITHUB_IMAGES_COMPLETE` Phase 5 run
→ worker `/phase6/prepare`
→ DeepSeek only when no reusable generated state exists
→ strict JSON parse
→ persist `generated_json`
→ deterministic validator + media-manifest cross-check
→ deterministic media path injection
→ deterministic YAML/Markdown assembly
→ persist exact Markdown + `post_path`
→ existing Phase 2 sub-workflow
→ persist draft commit and `DRAFT_CREATED`
→ stop.

The model never controls final media paths. The validator derives `featuredImage`, `thumbnailImage`, `gallery[].src`, and `routeGallery[].src` only from the durable Phase 5 processed manifest. Article filenames are derived separately from the generated title; Phase 5 media filenames remain immutable.

## DeepSeek contract

Phase 6 uses the existing n8n credential `DeepSeek - Travelling Trails`. During implementation on 2026-10-08 the current API was verified and the Phase 6 request was moved to `deepseek-flash`. The call is deliberately text-only: it sends the normalized trip, allowed schema values, and processed media manifest metadata, not source image bytes/base64.

The prompt explicitly states that media metadata does not prove photo contents. Alt/caption text must be grounded in explicit trip input; otherwise validation fails for required used-image alt text and a human review/update is required.

Output must be exactly one JSON object with the Phase 1 conceptual shape:

- `frontmatter`
- `bodyMarkdown`
- `imagePlan`
- `reviewWarnings`
- `missingInformation`

YAML is never generated by DeepSeek.

## Durable Phase 6 state

Phase 6 adds columns to the existing `runs` table, in place:

- `phase6_status`
- `phase6_last_safe_status`
- `phase6_error_message`
- `draft_markdown`
- `draft_commit_sha`
- `deepseek_call_count`

It reuses the existing reserved fields:

- `generated_json`
- `validation_errors_json`
- `post_path`

Status machine:

`NOT_STARTED → TEXT_GENERATING → TEXT_GENERATED → TEXT_VALIDATED → DRAFT_WRITING → DRAFT_CREATED`

`FAILED` is an explicit transient/error state. `phase6_last_safe_status` determines recovery.

Recovery rules:

- crash/failure before generated JSON: call DeepSeek again
- `TEXT_GENERATED` persisted but not yet validated: validate the stored result without another model call
- schema/business-invalid model result: persist validation errors, mark `FAILED` with no safe Phase 6 generation checkpoint, and allow regeneration
- `TEXT_VALIDATED`: exact `draft_markdown` and `post_path` are immutable retry inputs
- failure/collision during Phase 2: persist `FAILED` with `phase6_last_safe_status=TEXT_VALIDATED`; retry reuses exact bytes and skips DeepSeek
- `DRAFT_CREATED`: return `idempotent:true`, `action:NO_DRAFT_WRITE_NEEDED`; skip DeepSeek and Phase 2

Error text is bounded to 4000 characters.

## Validation and deterministic assembly

`automation/lib/phase6_draft.py` validates the current enums by reading `automation/lib/schema.js` and fails closed on unknown values. It additionally enforces:

- `draft === true`, `featured === false`
- durable trip date/author
- exact known top-level/front-matter fields
- category/travel type/ride mode/activity/tag enums; `post` tag required
- layout/TOC invariants
- non-empty title, description, body
- no body front-matter delimiter
- difficulty/season constraints
- no affiliate data without durable approval
- every image path belongs to the Phase 5 processed manifest and has the correct role
- no duplicate/unknown/path-traversal/local filesystem/data-image content
- deterministic title slug, post path, YAML, and Markdown bytes

## n8n behavior

n8n 2.40.7 supported `publish:workflow` / `unpublish:workflow`. Genuine sub-workflow tests required Phase 4 or Phase 2 to be temporarily published. Only the required workflow was published for each test window and both were restored inactive afterward. n8n itself was not restarted or recreated.

One-off `n8n execute` initially conflicted with the running task-broker port 5679. Genuine tests therefore used isolated one-off CLI `N8N_RUNNERS_BROKER_PORT` / `N8N_PORT` values; the production n8n process was not interrupted.

## Netlify acceptance exception

Live Netlify state did not match the Phase 5 handoff assumption. The public Netlify site API for site `travellingtrails1` showed production deploys and one historical `render-blog` branch deploy, but zero `Staging` deploys. The expected branch URL `https://staging--travellingtrails1.netlify.app` returned 404. Phase 6 did not change Netlify site configuration, per the explicit safety rule.

Therefore a Netlify **Staging branch rebuild could not be proven** in Phase 6 without changing Netlify configuration. The repository build and draft behavior are proven, but the strict Phase 6 definition of done remains blocked on enabling/confirming the `Staging` branch deploy outside this phase's allowed mutations.
